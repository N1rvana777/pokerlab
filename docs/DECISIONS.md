### D2 牌编码沿用 `card = 4*rank + suit`（实现）
与 `pokerlab.math.fast_eval` 和 postflop-solver 一致（rank 0..12 = 2..A，suit 0..3 = c,d,h,s），避免跨模块转换错误。

### D3 自写牌力评估器，不复用旧评估器或 PokerRL-Omaha（实现）
- 旧 `pokerlab.math` 评估器只返回牌型类别，不能比较 kicker（AGENTS.md 已注明）。
- PokerRL-Omaha 的 PLO 评估对 6 个底牌对分别做 Hold'em 7 选 5，不强制"恰好 3 张公共牌"；审计估计 18.7% 牌值错误、单挑 4.3% 摊牌判错（见 RESEARCH_NOTES）。
- 新评估器：标量参考实现 + NumPy 批量实现两套独立代码，用 2,598,960 手全枚举（7,462 个等价类、各牌型计数）和随机对照验证。

### D4 单手引擎规则（实现；均可配置或可改）
- 人数 2–8；单挑时按钮位下小盲、翻前先行动、翻后后行动。
- Pot-limit 上限（P/h/c 记号见 D15）：raise-to ≤ h + P + 2c；首注 ≤ P。引擎和求解树调用同一个 `pokerlab.plo.betting` 模块计算。
- 最小下注 = 大盲；最小加注增量 = 上一次完整下注/加注的增量；不足额 all-in 可以更小。
- 不足额 all-in 不重新开放加注：已行动的玩家只有在"自上次行动以来面对的累计增量 ≥ 一个完整加注"时才能再加注（TDA 式累计规则）。
  - 已知边界：玩家 check 后面对不足最小注的 all-in 下注，本实现同样不重开加注。规则手册对此有分歧，留作待确认（见"未确定"）。
- 面对下注才提供 fold；没有其他可行动的对手时不提供加注。
- 大盲不足额时 all-in 贴盲，其他人仍需跟满名义大盲。
- 前注是死钱，计入总底池；是否计入 pot-limit 上限由 `antes_count_for_pot_limit` 配置（默认 True；GTO Wizard 的 MTT 库两种口径都提供，说明行业惯例不统一）。
- 结算：任何人从每位对手处赢得的筹码，不超过自己投入的数额。具体顺序：
  1. 退回超过"最大未弃牌投入"的部分，例如已弃牌者的前注/盲注超过短码 all-in 的部分（2026-10-23 审查后修正，原实现在这种情况下会崩溃）。
  2. 退回最大投入者未被跟注的部分。
  3. 按投入层级拆分边池，只在未弃牌者之间比较。
  4. 平分时，零头从按钮左侧顺时针分配；单挑时这意味着给大盲。
- 抽水：默认无；`RakeRule(percent, cap, no_flop_no_drop)` 必须显式配置。按精确十进制计算后向下取整，并按各底池大小比例分摊（最大余数法）。2026-10-23 修正：原实现用浮点会少算 1 个筹码，而且先从主池全额扣除。
- 前注先于盲注贴出：筹码不够同时付两者时，玩家只够付前注就 all-in 了。TDA 的 big blind ante 格式是盲注优先，本实现不同；需要时再加选项。
- 翻前的 pot-limit 上限用实际贴出的筹码计算；需跟注的金额仍是名义大盲。
- 不足最小注的 all-in 下注（例如 50，大盲 100）之后，最小加注到 50 + 大盲 = 150。
- 简化（已写入代码说明）：移动按钮（无 dead button 规则）、摊牌时所有未弃牌者亮牌、单次发牌（无 run-it-twice）、无 straddle。

### D5 单手状态与跨手 session 分离（实现，响应用户要求）
- `HandState` 只管一手；`run_session` 管多手。
- `reset` = 固定 root：每手从配置筹码开始、按钮每手移动一位。
- `carry` = 筹码延续。0 筹码玩家的处理由 bust_policy 决定：`rebuy`（补回起始筹码，计入 rebuy_chips，不算赢利）、`leave`（离座，少于 2 人则结束）、`stop`（结束 session）。
- 两种模式都在每手和整个 session 层面断言筹码守恒（含抽水和补码）。

### D6 Agent 只能看到 `Observation`（实现，响应用户要求）
- 模拟器全状态（所有底牌、预定公共牌）与观察对象分离。
- `observe()` 只放入本人底牌、已发公共牌和公开动作；手牌结束后只给 `PublicHandSummary`（亮牌者底牌、已发公共牌、公开动作、净输赢）。
- 测试方法：把观察者看不到的牌全部重新发一遍，重放同样的公开动作，观察对象必须完全相同。

### D7 收益口径：线性净筹码（用户）
- 评测报告 bb/100 = 每手平均净筹码 / 大盲 × 100，附标准误和 95% CI。
- 不使用底池平方奖励（AMP3 那种设计与线性利润目标不等价）。
- 默认无抽水；补码不算赢利。

### D8 首个求解目标：单挑 PLO4 河牌子博弈（用户范围；算法细节为实现）
- 向量形式 CFR 族，交替更新。算法可选：`cfr`、`cfr+`（Libratus 子博弈求解所属家族）、`lcfr`（Pluribus 蓝图早期使用的线性加权）、`dcfr`（默认 α=1.5, β=0, γ=2）、`es-mccfr`（每次遍历采样一手对手底牌及对手动作，遍历者底牌向量化、动作全展开，可选线性加权）。
- 默认 DCFR 的理由：
  - 在本项目的小型 LP 对照里收敛最快，3,000 次后 0.0005% pot。
  - 现有 Hold'em 引擎和 Abstraction Agent 实验也用它。
  - 参数 3/2、0、2 是原论文的推荐值，已核对 arXiv 1809.04040 原文。
  - 这是经验选择，不是理论结论。
- 收益口径与现有工作台一致：起始底池视为沉没，u0 + u1 = pot。报告同时给出 `value_net_of_equal_sunk_share = value − pot/2`，即双方各投入一半沉没底池时的零和净值（HU 每条街开始时都是这种情况，Kuhn 的前注也是）。
- exploitability = NashConv/2 = (BR0 + BR1 − pot)/2，换算为起始底池的百分比。
  - 默认评估平均策略，最后一次迭代的策略另行报告。
  - 最佳回应只在抽象树的动作里、按信息集（己方手牌, 公共节点）选择。
  - 常数偏移不影响这个值：零和下 BR_p − pot/2 相加，结果相同。
- 精度只对给定范围和离散 pot-limit 尺寸树成立，不对整局游戏或树外尺寸成立。

### D9 首轮范围：显式输入或固定种子均匀抽样（实现，用户允许受控范围）
- 范围是输入假设，不来自蓝图，所以解是"该子博弈"的均衡。
- 两边手数乘积 ≤ 400 万用稠密矩阵；更大（含全范围 178,365 手）用容斥卡牌移除 + 按牌力排序前缀和，复杂度线性。

### D10 正确性以独立参照为准（实现，响应用户要求）
- 算法用 Kuhn 已知值（−1/18）检查。
- 小型 PLO 河牌用三种独立参照核对：序列形式 LP（SciPy HiGHS，原始/对偶两套）；逐手循环的最佳回应（标量评估器 + 集合不相交判断）；稠密矩阵与容斥两套摊牌实现互相核对。
- 另外核对：求解树的每个动作在单手引擎中合法，且 1.0 pot 尺寸恰好等于引擎的 pot-limit 上限。

### D11 检查点与输出（实现）
- 检查点为 `.npz`，包含 regrets、累计策略、迭代数、RNG 状态、配置、子博弈指纹；先写 `.partial` 再原子替换。
- 续算按指纹拒绝不匹配的子博弈；测试要求"中断 + 续算"与"连续运行"逐位一致（DCFR、CFR+、ES-MCCFR）。
- CLI 拒绝覆盖已有输出，与现有工作台"已存在输出不会覆盖"的约定一致。

### D12 评测入口（实现，响应用户要求）
- 固定 root 下默认用 duplicate。
  - 每个座位轮换是一场独立比赛，由按规格新建的 agent 来打，所以 agent 不会在重打同一副牌之前看到它的公共牌或摊牌。2026-10-23 审查后修正：原实现让同一个 agent 实例连续重打同一副牌，会记忆的 agent 能借此知道对手底牌。
  - 每副牌的基础座次是一个固定种子的随机排列，再按轮换平移。这样每个 agent 在每副牌里恰好坐过每个座位一次，而 agent 之间的相对座次在不同牌之间变化。
  - 标准误按"每副牌"为独立块计算。对不学习的 agent 这是精确的；如果 agent 在同一轮换内学习，只是近似。
- carry 模式用批均值估计标准误，并注明因筹码延续而相关、结果只是近似。
- 报告字段：规则、人数、起始深度、reset/carry、对手版本、样本数、单位、墙钟/CPU 时间、进程峰值内存、代码指纹。
- 赢 random/rule bot 只作功能检查。

### D15 下注抽象：四档精确比例 + 边界动作（2026-10-23，用户）
- 记号：P = 行动前总底池（含本轮已投入的所有筹码），h = 行动者本轮已投入，c = 跟注还需补入。
- 公式：pot_after_call = P + c；max_raise_to = h + P + 2c；fractional_raise_to = h + c + f(P + c)。首注 h = c = 0，即 f·P。
- 默认 f ∈ {1/3, 1/2, 2/3, 1}，下注和加注都用这四档。比例是精确有理数（`fractions.Fraction`，配置写 "1/3" 等），筹码四舍五入（.5 向上），全程不用浮点。下注和加注的比例可以分别配置。
- 每个可下注/加注的节点：
  - 合法窗口外的比例尺寸直接丢弃，不夹到边界。
  - 加入两个边界动作：最小合法下注/加注（筹码不足时为短码 all-in），以及最大值（pot 尺寸加注；筹码低于 pot 上限时为短码 all-in）。两者可分别关闭：`include_min_raise`、`include_max_raise`（旧名 `include_all_in`）。
  - 超过 pot-limit 的 all-in 不会出现。最后去重。
  - fold/check/call 按情形提供。
- 加注次数上限 `max_raises` 默认 2（开局下注不算加注）。它必须写进配置和报告。
- 旧示例的三档结果已被重跑结果取代（PROJECT_STATE 记录新数值）。全范围规模测试保留一个显式的"精简树"配置（只有 pot 尺寸、1 次加注），用于复现原 0.729% 结果。

### D16 HU 决策接入：前三街基线、河牌求解（2026-10-23，实现，响应用户要求）
- 前三街：`baseline-v1`。这是固定、可复现、按手牌向量化的策略：牌力百分位经 logit 得到 fold/passive/aggressive 三类概率，每类下限 eps=0.01；aggressive 用 2/3 pot 尺寸；带版本号。
- 河牌 range：
  - 先用占位牌重放公开动作，得到每次决策的公开情境（是否需跟注、能否加注）。
  - 对不与公共牌冲突的 178,365 手做均匀先验，乘以每个公开动作在 baseline-v1 下的类别似然（Bayes）。对手模型就是 baseline-v1，因此对其他对手是错设的，报告中注明。
  - 决策端不读取模拟器里的对手底牌或未发的牌，只用 `Observation`。
- 每方按后验做 `range_samples` 次有放回抽样（固定种子，次数作为权重）；自己的手牌若未被抽到则补入，权重 1。
- 求解：在河牌开始处做 unsafe 求解（DCFR，默认 200 次迭代，四档抽象，max_raises 2），按平均策略对自己的实际手牌抽样行动。
  - 对手做出树外下注/加注时，从当前状态重解。range 先按前一解的树内动作概率加权（下限 1e-3），树外动作本身不更新 range。
- 每次决策记录：
  - 前序策略版本、range 更新步骤（含有效手数）和抽样种子；
  - 求解配置、树规模，以及该次求解的 exploitability；
  - 延迟分解（range、求解、查询、总决策）。诊断用的 exploitability 计算不计入决策延迟。
- 范围界定：这只是"独立河牌求解"，不是全局 safe 重解，也不说明完整 PLO 达到均衡。对局收益只用于功能验证和基线比较。

### D18 当前里程碑：受控的 turn + river 联合求解（2026-10-23，用户范围；实现细节为实现）
- **博弈定义**：固定 4 张 turn 公共牌，显式加权 range，可配置的底池和筹码，两街都用四档精确比例加边界动作。turn 和 river 的加注上限分别配置，必须写入报告。
- **河牌**：枚举全部 48 张，不抽样。持有河牌的手牌在该河牌下 reach 为 0；每对不相交手牌的发牌概率为 1/40。
- **一次联合 CFR**：同时优化 turn 和全部 river 信息集，turn 取值经由 river 策略回传。不把独立求解的 river 策略拼接起来当作 turn 均衡；拼接法只作为对照，用来测量它的 exploitability。
- **实现**：river 数组按 48 张河牌批量处理；每张牌的摊牌用稠密矩阵，n0·n1 ≤ 250,000。更大的 range 要先实现按河牌的容斥摊牌或牌力抽象。
- **验证**：tiny 实例上与联合序列形式 LP、逐手循环最佳回应、发牌概率暴力归一化三者核对；检查点续算逐位一致。
- **结论范围**：只对给定的 turn 子博弈成立。

### D19 决策预算诊断的结论（2026-10-23，依据实测；会影响后续规模）
- **样本内 exploitability 不能代表质量**：agent 式的 150 手抽样 range 河牌求解，样本内 exploitability 约 0.1% pot（200 次迭代）。但用最近牌力规则扩展到参考 range（约 1,950 手）后，在参考游戏中的 exploitability 为 8.7–19.1% pot（全部 18 个抽样配置），而且增加迭代或抽样到 400 手都不会改善。所以样本内数字不能当作原始游戏的策略质量。
- **直接求解参考游戏**：200 次迭代 0.09–0.13% pot，500 次 0.022–0.027%。同样迭代次数下，耗时是 150 手抽样求解的 35–41 倍。
- 数据：`outputs/plo/v4/budget-clean.json`，与先前的 `outputs/plo/diagnostics/budget.json` 的 44 个 exploitability 数值逐位相同，只有计时不同。
- **决定**：以"接近均衡"为目标的后续工作，不再以小样本抽样 range 作为主要求解路线。改为在完整 range 上直接求解（容斥摊牌、提速），或者用有精确参照的牌力抽象。agent 的抽样河牌求解只保留为功能演示。
- **2026-10-25 归因更正**：控制实验在同一参考问题上（paired_flush，k=150、200 次迭代）把误差拆开了（PROJECT_STATE §4.12）。
  - 流程本身没有错：k=N 时经过同一个映射，exploitability 与直接评估同为 0.0220%，策略变化为 0。
  - 只换抽样（未抽到的手牌用参考解自身的策略）：0.32% pot。
  - 只换映射（被抽到的手牌用精确的参考解，其余按最近 river 牌力复制）：44.9% pot。
  - 用户 2026-10-25 的修正：在当前控制实例中，最近河牌排名映射是已确认的大误差来源；实际 agent 的采样及逐手重解误差尚未量化。这些替换实验不是可相加的误差分解。"只换抽样"一行里，未抽中的手牌用的是精确策略，所以 0.32% 不能证明实际 agent 的采样误差很小。
  - 8.7–19.1% 里，已确认的大误差来源是"最近牌力复制"这条映射规则：牌力相同的手牌因阻断牌不同而策略不同，按首个决策节点算的平均总变差为 0.36–0.38。它不能归因于抽样不足。
  - 这个评测对象（固定的小范围解 + 映射）也不是 agent 的决策规则：agent 总是把自己的手牌放进抽样博弈里求解，不经过映射。agent 自身的误差没有测。
  - 修正后的决定：不再用"抽样解 + 最近牌力映射"给未采样的手牌提供策略。决策时按手牌重新求解的抽样路线，质量尚未测量，保留为未定。

### D20 资源与性能的判断（2026-10-23，依据实测；本轮不创建付费资源）
数据见 PROJECT_STATE §4.11（`outputs/plo/v4/resources.json`、各 turn 报告，以及 NLHE 的原有运行记录）。
- **PLO 求解器（Python/NumPy）：瓶颈是单核计算效率和算法规模，不是内存容量，也不是 GPU。**
  - 除稠密矩阵乘以外，各阶段 CPU 时间/墙钟时间都在 0.9–1.04 之间，也就是 24 个逻辑核里只有 1 个在忙。只有稠密 BLAS 阶段达到 3.6。
  - 进程峰值最大是全范围四档河牌的 1,146 MiB；turn 子博弈不超过 0.8 GiB。都远低于本机 32GB。
  - 代码没有 GPU 路径，RTX 5080 没有被使用。
  - 规模：全范围四档河牌每次迭代 19.2 s。全范围 turn 按实测节点数要 42GB 到 14.5TB，必须先做抽象（见 ARCHITECTURE）。
- **旧 NLHE 工作台（Rust 原生，16 线程）：限制是内存容量和并行效率。**
  - 目标完整树的计划需要 13.2–14.3GiB，而 Windows 宿主的安全预算只有 11.1–11.5GiB，运行在分配前被拒。
  - 完整运行期间，16 个线程约有 11 个核在忙，其中约一半是内核时间。复用临时缓冲后，迭代快了 7.9 倍。
- **判断：现阶段不需要云资源。**
  - PLO 求解器只用到 1 个核，换一台核更多的机器不会变快。要先并行化（例如按 48 张河牌分片）或重写热点内核。用 Rust 还是 numba 仍未定。
  - 云实例的规格与费用估算只供参考，见 PROJECT_STATE §4.11。本轮没有创建任何资源。
- **2026-10-25 补充**（turn + river 换成容斥后端之后，PROJECT_STATE §4.13）：
  - 内存：摊牌结构从每张河牌 n0 × n1 降为线性。1,485 × 1,480 时为 69 MiB，稠密后端约要 3.4GB。现在内存的大头是 regret 与累计策略（821 MiB），它们随 river 决策节点 × 手数 × 动作增长。
  - 时间：win 核仍占约 73%。按河牌分块的线程把 1,485 × 1,480 的每次迭代从 25.2 s 降到 15.4 s（4 个线程，1.63 倍），内存只多约 2 MiB。剩下的串行部分（regret 更新、稀疏 compat）限制了加速比。
- **旧 NLHE 约 11GiB 安全预算的来源**（只诊断，没有调整阈值）：
  - 预算在每次启动时现测：min(24,576 MiB 上限, WSL 可用内存 − 512 MiB, Windows 可用内存 − 2,048 MiB)，见 `src/pokerlab/solver/resources.py:57`。
  - 2026-10-16 被拒的那次：Windows 可用 13,387 MiB，安全值 11,339 MiB（11.07GiB），比 WSL 的 14,709 MiB 更紧；计划 13.23GiB 大于 11.07GiB，于是拒绝。
  - 2026-10-13 成功的那次（峰值 RSS 13.85GiB）：Windows 可用 18,026 MiB，安全值 15,978 MiB；WSL 安全值 14,727 MiB 更紧，成为预算。计划峰值 14.25GiB，符合预算。
  - 两次是同一台机器、同一个 WSL 配置（约 15.8GB）、同样的预留。差别在启动时 Windows 被其他程序占用的内存。

### D22 turn + river 的容斥后端与线程（2026-10-25，实现，响应用户要求）
- `showdown: "auto"` 在 n0·n1 ≤ 250,000 时用稠密后端，更大时用容斥后端。稠密后端保留，作为小实例的参照。
- 后端是计算方式，不属于博弈本身，不进子博弈指纹。所以同一博弈的检查点可以换后端续算，数值在浮点误差内一致。
- 验证用值，不用策略：两种后端的质量相差 1e-15，随机策略下的价值和最佳回应相差 5e-13，都收敛到联合 LP 值。
  - 单个平均策略可以不同：从第 2 次迭代起，舍入会把恰好为 0 的 regret 翻成正或负；这个子博弈有很多均衡。
- `--workers N` 是按河牌分块的线程，只并行 win 核。CFR 状态与 N 无关、逐位相同；N 不改变求解语义。

### D23 联合策略接入决策（2026-10-25，用户范围；实现细节为实现）

### D24 手牌抽象 v1（2026-10-25，用户要求；具体实现由 Claude 选择）

  - 在同一组 range、动作树和筹码下，对比精确参考解、旧的最近牌力映射、按牌力分组的抽象（rank）、只按胜率的抽象（eq_only）和 v1。

### D38 Node Lock 分两种（2026-11-01，用户问 Node Lock 是否实现；实现细节为 Claude 的选择）

### D39 Player Profile 用激励实现（2026-11-01，实现细节为 Claude 的选择）

## 未确定（待讨论，不是决定）
- 更大的树（每街 3 个尺寸约 25.6GB）要不要加 WSL 内存或租云机器：等用户决定，"不买云算力"的约束不变。

- turn/flop 求解的规模路线：在当前表示方式下，全范围 turn 仅 regret 和累计策略就要约 42GB 到 14.5TB（按实测节点数估算，不是理论下界，见 ARCHITECTURE），本机不可行。可选的方式包括更紧凑的表示（float32、去掉死手、压缩 regret）、花色同构、牌力抽象（分桶）、机会采样（MCCFR），以及 depth-limited + 叶节点估值，尚未比较和选定。
- 多人（3–8）求解方式：Pluribus 式的 unsafe nested search + 多个延续策略，还是固定对手的回应求解。多人没有均衡保证。
- 是否实现 Libratus 式 safe/nested 重解（gift、margin）以及树外尺寸处理。
- 河牌 agent 目前按平均策略行动。是否改为最后迭代（Pluribus 搜索的做法），是否需要 range thresholding 这类后处理，都还没定。
